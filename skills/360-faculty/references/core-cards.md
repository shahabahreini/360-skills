# Core Cards

Starting Cards for common seats. Adapt the questions to the plan; never reuse them unchanged. Every seat must still meet the Card rules in `SKILL.md`: at least three named techniques, critique tests that cite the plan, and a concrete deliverable. Derive Cards for roles not listed here from the same fields. For the wider catalog of roles, see `seating-roster.md`.

| Faculty | Owns | Techniques | Critique tests | Innovation move |
|---|---|---|---|---|
| Software architect | Boundaries and irreversible choices | Dependency mapping, reversibility check, ADR-style trade-off, change-cost analysis | Which choice is expensive to undo? Which module changes for the most unrelated reasons? What can the existing structure absorb? | Replace a new layer with a seam in existing code |
| Simplifier | The shortest design that covers every requirement | Deletion test, requirement-to-task tracing, reuse audit, YAGNI check | Which task has no objective? Which abstraction has one caller? What would the plan look like at half the code? | Merge or delete a task and report what it saves |
| ML engineer | Whether the model work yields a trustworthy result | Baseline-first comparison, data-leakage audit, train/validation/test split review, error analysis by slice, reproducibility check (seeds, versions) | Is there a simple baseline to beat? Can test data leak into training? Which slice fails first? | Add a slice-level error report instead of another model |
| Evaluation specialist | Claims backed by numbers | Metric-to-goal mapping, held-out set design, confidence intervals, ablation, regression suite | Does the metric measure the stated goal? How many samples before the gap is real? What would show the result is noise? | Turn one ad hoc check into a repeatable regression set |
| Agent architect | Tool use, memory, handoff, refusal | Tool-contract review, failure-loop analysis, permission scoping, context budgeting, human-approval gates | What stops an infinite loop? Which tool call is irreversible? What does the agent do when a tool fails? | Drop a tool or memory store the task never needs |
| Application-security engineer | Threats in this design | Threat modeling (STRIDE), abuse-case writing, secret-handling review, trust-boundary mapping | Where does untrusted input enter? What happens if a credential leaks? Who can call this who should not? | Close a hole by removing an entry point, not adding a guard |
| QA strategist | What must be proven, and at what cost | Risk-based test selection, boundary-value analysis, equivalence classes, regression targeting | Which failure would a user notice first? Which test would catch the likeliest bug? Which planned test proves nothing? | Replace several brittle checks with one risk-targeted check |
| Observability engineer | Whether a failure can be seen and reproduced | Signal-per-failure mapping, log-structure review, trace-point selection, alert-noise audit | How would we know this failed in production? What is needed to reproduce it? Which signal will nobody read? | Add one signal that answers the top failure; remove unread ones |
| Content designer / UX writer | Words the reader can act on | Plain-language edit, task-first ordering, before/after phrasing, reading-level check, term audit | What does the reader do after this line? Which term is undefined? Where does the reader get lost? | Rewrite a section as outcome first, then evidence |
| Reliability engineer | Graceful failure and recovery | Failure-mode and effects analysis, idempotency check, retry/timeout review, rollback rehearsal | Which step breaks on retry? What state remains after a half-finished run? How do we undo this? | Make a step idempotent rather than adding a recovery service |
